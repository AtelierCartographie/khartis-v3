# DuckDB data layer

All data work (import, typing, summary stats, sort, search, filter, calculator, join, reprojection, classification, aggregation, export) runs through DuckDB WASM with the `spatial` extension. Reference: `docs/IMPORT_DUCKDB.md`.

## One engine, reached through its layers

- Read files with DuckDB functions: `read_csv`, `read_parquet`, `ST_Read`. Adding a format follows the checklist at the end of `docs/IMPORT_DUCKDB.md`.
- Use `dataPipeline.processFile()` and `duckDBOrchestrator` for high-level operations. `Duck.query()` is for low-level SQL inside the `duckdb` feature.
- Other features import from the `duckdb` barrel (`$lib/features/duckdb`), not from its internals.
- `static/duckdb-extensions/` is generated by `pnpm download:extensions` (run on postinstall) and follows the DuckDB WASM version. It is not edited by hand.

## SQL: escape everything derived from user files

Table names, column names and values almost always come from user files (`sanitize.utils.ts`):

- Identifiers go in double quotes through `escapeIdentifier()`: `"${escapeIdentifier(col)}"`.
- String values go in single quotes through `escapeSqlString()`: `'${escapeSqlString(value)}'`.
- An inline `table.replace(/"/g, '""')` or a raw concatenation is the bug this rule exists for.

## Geometry: keep the source CRS, reproject when rendering needs it

- Imported geometry stays in its source CRS. The orthographic engine renders it as is, which is what lets Khartis display already-projected files and offer arbitrary d3 projections. A blanket reprojection to EPSG:4326 on load would break that.
- Reproject to EPSG:4326 with `ST_Transform` only when the render path needs WGS84: a tiled or MapLibre basemap is active, or the user applies a d3 projection to a non-WGS84 dataset (the d3 stream of `geoarrow-deck-stream` accepts lon/lat only). Client-side proj4 is the fallback when `ST_Transform` fails.
- Return geometry as Arrow IPC and stream it (`queryStreaming`), so a large dataset does not exhaust WASM memory. The binary buffer feeds `geoarrow-deck-stream` directly (see `render-pipeline.md`).
- Keep tabular results as Arrow tables. Materialize JS arrays (`toArray()`) only at the UI boundary that needs rows.

## Joins: exact first, then a bounded fuzzy phase

- A table-to-basemap join matches normalized values exactly, then compares only the unmatched values with Jaro-Winkler. The fuzzy phase is bounded by a pair budget (`MAX_FUZZY_AUTO_PAIRS`); past it, suggestions are computed on demand.
- Rows are graded with `JoinStatus` (joined, to verify, duplicate, unrecognized, ignored). Every bucket is shown with its count; unmatched rows are never dropped silently.
- The grading cutoff `FUZZY_SEARCH.SCORE_CUTOFF` comes from a calibration on a labelled corpus of name pairs and is locked by `tests/duckdb/macros-join.test.ts`. It changes only with a new calibration.
- The on-demand fuzzy pass cannot be cancelled: DuckDB WASM is single-threaded and `cancelPendingQuery` rejects only when the computation ends. A Cancel button on that path would lie.

## Mutations invalidate caches

- After a statement that changes a table (`CREATE OR REPLACE`, `DROP`, `ALTER`, `UPDATE`, `INSERT`), call `markTableMutated(ctx, table)` so cached stats and search results do not go stale.
- After a DDL that adds columns, Arrow streaming can return those columns as `NULL`. Joins, GPS and direct reads therefore skip streaming (`skipStreaming`) on purpose.

## Errors and NULLs

- Throw `PipelineError` subclasses (for example `DuckDBError`) and surface them with `showError` or `showWarning`, localized through Paraglide. A swallowed query error or a bare `console.error` hides the failure from the user.
- Which tokens mean "missing" is configured per project. Rely on that NULL set instead of testing only `''` or `null`.

## Tests

- SQL, macros and readers are proven in `tests/duckdb/` against a real DuckDB through `@duckdb/node-api` (`tests/pipeline/duckdb-node-helper.ts`): run the statement and assert on the rows.
- A test that mocks `executeQuery` and asserts on the SQL string mirrors the implementation. Keep one only when no real-engine test can reach the behavior. `testing.md` holds the full criteria.
